Junk-document discard deployed 2026-08-20 23:13 CEST (migration 0021 applied, backfill run — 9 of 18 documents discarded, `nightly-verify` OK on 47 events / 18 files afterwards; the migration must go from the homelab HOST BEFORE the new web/worker images, or every Discard click 500s on `invalid input value for enum doc_status` with the ledger event already written) (migration 0021, additive `doc_status` value `discarded`): `gmail-auth.ts` no longer promotes message parts that are `Content-Disposition: inline` AND carry a `Content-ID` (the `cid:` images an HTML body embeds), which were 56% of all filed attachments; the decision is the pure `isInlineBodyImage` in `apps/worker/src/gmail-parts.ts`, and a part with malformed headers is KEPT, never skipped. Discard is a third `doc_status`, appended through `document_status_changes` with its ledger event — never a delete, because `documents` is append-only and already carries a `document.ingested` event. THE TRAP: discard is never written back to `documents.status`, which reads `"inbox"` forever, so every filter must resolve the effective status via `effectiveDocument` — the surfaces that do are `documents.list` (default-excludes, filtered in SQL BEFORE the LIMIT so discarded rows cannot eat an evidence picker's page budget; `includeDiscarded: true` opts in), `suggestions.list`, `dashboard.stats.pendingSuggestions`, `suggestions.approveEntry` (`proposed.attachmentDocumentIds` is an INGEST-TIME snapshot and is re-resolved at approval, or a discarded logo lands back in `entry_documents` and in the signed export), `search/retrieve.ts` and `search/recent.ts` (the ⌘K palette's empty state, which a discard's reindex would otherwise push to position #1). A SECOND trap under it: `search_chunks.status` is denormalized per chunk and the status renders into the TOP of the body only, so on a multi-chunk document only chunk 0's `source_hash` changes — `indexEntity` therefore refreshes status/occurred_at on text-unchanged chunks WITHOUT re-embedding them, otherwise chunks 1..n keep a stale status and one of them is enough to resurrect the document in search. `document.updated` is recomputed from the live `document_status_changes` row by `resolveDocumentUpdatedHashes` in `verification.ts` (matched rows are CONSUMED, so an identical duplicate cannot vouch for two events) — without it an UPDATE on that table hides a document from every surface while /verify reports ok. Search filters with `IS DISTINCT FROM 'discarded'`, not `<>`: `NULL <> 'discarded'` is NULL and would drop every entity type that has no status. Vault bytes are NEVER purged: it would reclaim ~1% of the vault, the image stays inside the archived `.eml` anyway, and it would teach `nightly-verify` that some missing files are acceptable. "Always discard" needs no rule table — `ingestDocument` dedups on sha256, so a discarded document stays discarded for those bytes forever. A collapsed "Discarded" section on `/vault` lists them (`documents.list({ status: "discarded" })`), because otherwise a document discarded by mistake is reachable only by typing its UUID and the Undo button cannot be found. Backfill the ones already filed with `pnpm --filter worker discard-signature-images` (idempotent; matches `source='email-attachment' AND title='image.png' AND created_at < 2026-08-21`, because the disposition header is gone post-hoc and `image.png` is also what a pasted-from-clipboard screenshot is called; only documents still in the inbox are touched, so a `filed` judgement always wins; one ledger event each, each individually undoable). The Gmail port skip requires `image/*` mime AND inline AND a `Content-ID`: macOS/iOS Mail marks EVERY attachment inline with a Content-Id, so disposition alone would drop a mailed Beschikking.pdf unrecoverably (pollGmail short-circuits on a seen message id). Every skipped part is written into the `gmail` worker run. THE TRAP: accounts are never merged. Under bewind Martin's money moves between a beheerrekening and a leefgeldrekening (VerderGroep took over the ABN account in early August 2026), so one undifferentiated series draws a collapse at the handover that never happened — `buildMoneySeries` returns one `AccountSeries` per `account_iban` and rows with NULL form their own "unknown account" series rather than joining a known one. A SECOND trap: income is RECURRING ONLY, but "recurring" is a fact about the PAYER and never about the amounts — `detectRecurring`'s 40% amount gate is SKIPPED in the credit direction (`14fc32a`), because TrueFullstaq paid € 648,00 / € 2.660,68 / € 1.118,65 in three consecutive months (the last a part-month, Martin left 10 June) and the gate threw the whole salary away, drawing € 0,00 for April and May in months where € 5.006,31 arrived; money from a counterparty with a cadence is that line's income WHATEVER its size, a vakantiegeld from the employer's own IBAN included — it just must never set the projected figure — while a one-off from a stranger (belastingteruggave, an OpsMate invoice) forms no group of two and is disclosed per month as `incidentalCents` plus `incidentalRows`. The disclosures block under the chart is what makes the arithmetic reconcile, and removing it makes the page lie (the dashboard block deliberately shows no totals beyond the bars for the same reason: a summary that quietly dropped the disclosures would be a rounder story); each total is summed FROM its row list rather than filtered a second time, which is how a disclosure otherwise stops adding up. Income survives an employer change through the continuation rule in `incomeLines` (Martin switched employers in June 2026, so without it May–August show no income at all); the tolerance is `INCOME_CONTINUATION_TOLERANCE_NUM/_DEN` = 1/2, a MEASURED integer ratio and no longer the 0.25 guess — 0.25 refused his real 33,7% raise (€ 2.660,68 → € 3.556,42) and reported his income as ended and something smaller as begun — and the two lines are compared on `fullPeriodAmount` (median of every amount within 15% of the line's largest), NOT on medians, because a part-month at either end of a job change drags a median down; the obvious fallback for `fullPeriodAmount`'s known vakantiegeld hole is REFUSED on measurement and the numbers are in the comment on it. `splitInternalTransfers` CONSUMES a matched debit (the same discipline as `resolveDocumentUpdatedHashes` above): without it one € 500 transfer out disqualified TWO € 500 credits, erasing € 1.000 of income and disclosing twice what had moved; credits are walked oldest-first and take the nearest-in-time unclaimed leg so the answer never depends on row order. Statement coverage is inferred from each statement's first and last booking, computed in AMSTERDAM CALENDAR DAYS with abutting statements MERGED — a June exported as 1–15 plus 16–30 abuts rather than overlaps, and an overlap-only merge hatched a month every row of which is present, while UTC-instant arithmetic disagreed with `monthKey` by the offset — and it understates a quiet month on purpose: a month that is not provably complete renders hatched, and a month with no rows renders `geen data`, never €0. `money.month` reads a SQL window TWO DAYS WIDER than the month on each side and still pairs the exact month with `monthKey` in JS: month membership is an Amsterdam question, so an exact UTC window would drop the boundary rows the JS filter has to judge — widen the SQL, decide in JS. A parse-error row inherits the statement's account when every readable row in that file names the same one, and takes that import's EARLIEST readable booking rather than `new Date()`, or one unreadable line invents a permanent hatched "onbekende rekening" card on /money, dated today, forever. A THIRD trap, in the chart: the projection starts at the month AFTER the last COMPLETE month, which is normally the partial newest month that is already drawn as an actual — `moneyColumns` in `apps/web/src/lib/money-columns.ts` (pure, unit-tested without React) drops that overlap per account, so a four-month history never renders as five columns with `jul '26` twice; column keys are kind-qualified for the same collision, and only actual months are drill targets because the panel below the chart lists bank rows. `detectRecurring` in `@verder/parsers` gained a `direction` option defaulting to `"debit"` so no existing caller changed. Nightly dump now excludes `search_chunks` data, so a restore is only correct if it ends in `pnpm --filter worker reindex` (flags `--entity= --since= --prune`; there is no env-var form). Text extraction for documents ingested before the feature: `pnpm --filter worker extract-texts` (idempotent; also retries anything stored as extractor `none` on a mime extraction might now handle — PDFs, images, both spreadsheet mimes, and the uninformative ones like `application/octet-stream`, which is what ABN's export is recorded as). ## Project laws
- Evidence tables are append-only (enforced by Postgres grants); every evidence mutation appends a `ledger_events` row in the same transaction. Never weaken this.
- AI output is suggestion-only; nothing enters the ledger without Martin's approval. Model suggestion + verdict + edit diff are always recorded (golden rule: self-improvement).
- Tone: supportive/encouraging toward Martin; short, professional, official register for anyone else.
