Fixing it also forced `documents.update`'s no-op guard to treat an absent field as "no opinion", which repaired a second latent bug: a second discard of a RENAMED document left `previousStatus = "discarded"`, so Undo would have silently unfiled a filed document. THE TRAP THE WHOLE-BRANCH REVIEW CAUGHT AND NO TASK COULD: `browse`'s `bundel` branch filtered `bundle_documents`, which a RULE bundle deliberately has none of — so every rule bundle showed a count in the tree, "niets in deze tak" in the table, and downloaded the right files from its card. It now resolves through `bundleWhere` in `routers/bundles.ts`, the same predicate `resolveBundleDocumentIds` uses, so count, table and zip are one definition; `documents-browse.test.ts` walks EVERY branch the tree emits AND every bundle, asserting `browse(branch).total` equals its count. A SECOND one from the same review: an EMPTY soort key is a real branch (76 of 84 live dev documents), and `files-url.ts` decoded `"soort:"` back to "alles", so `Zonder soort` was unclickable and never highlighted. `docTypeKeySql` and `receivedMonthSql` live in `effective-status.ts` (a leaf importing only drizzle) because `documents.ts` now imports `bundles.ts`, and both are built by a `sql` template at MODULE SCOPE — a cycle would resolve to undefined at load, not merely lint. Three code paths fold a soort key (tree, browse, `ruleWhere`) and they are the SAME constant by identity, which is what makes the agreement mechanical rather than documentary; `docTypeKey` in `doc-type.ts` is the JS spelling of it and the only one a rule's literal input may use. The zip is hand-rolled STORE-only in `packages/core/src/zip.ts` — everything in this vault is already compressed, so deflate buys 0–3% for real CPU in a request path, and the alternative was a dependency in that path for one feature of one format. NO ZIP64: `ZIP_MAX_ENTRIES` 500 and `ZIP_MAX_TOTAL_BYTES` 512 MB, and the byte cap is a MEMORY bound (each entry is buffered so its CRC32 can go in its own header; a data descriptor is the upgrade path). `MAX_IDS = ZIP_MAX_ENTRIES - 1` in the route, because the `inhoudsopgave.txt` is itself an entry. Every file's bytes are read BEFORE one byte of the response is written — a missing file is a 409 naming it, never a silently short archive. THE SENDER NEVER GUESSES, and this cost four review rounds: `senderAddress` in `apps/worker/src/gmail.ts` refuses any parenthesis, any second top-level `<`, anything but whitespace after the `>`, and any top-level `,`/`:`/`;`, then matches the candidate whole against one ASCII regex — because three earlier versions that PICKED an address out of a header were each defeated by attacker-controlled text (`"demi@verdergroep.nl" <attacker@evil.tld>` beat first-address; a trailing RFC 5322 comment beat last-address; a `quoted-pair` escape beat a comment-stripper). A refused header costs an "Onbekend" a human corrects; a parsed one is permanent, because `documents` has no UPDATE. Migration 0033 exists ONLY because 0032's backfill joined `lower(p.email) = lower(r.from_addr)`: `raw_emails.from_addr` holds a WHOLE RFC 5322 header for Gmail-era rows (measured in prod: 107 of 130 header-shaped, 23 bare — `gmail-auth.ts` stores `headers.from` verbatim while the JMAP port stores a parsed address), and SQL `lower()` is the Unicode-aware fold `mail/relevance.ts:26-39` forbids for addresses. 0033 ports the worker's fail-closed rule into SQL and is idempotent (`party_id IS NULL` only), so it is safe to re-run. NOTE `senderAddress`'s output feeds a column `/verify` does NOT cover — `document.ingested` returns its stored payload hash and only re-checks the file bytes — so the "cannot be corrected" guarantee rests on the missing UPDATE grant, not on tamper detection.
